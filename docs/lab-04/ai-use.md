## Reflection
I treated the Lab 4 specification as the contract for every issue. Writing `specification.md`, `ui-spec.md`, `api-spec.md`, and `tests.md` first forced me to settle the business rules, the status matrix, and the error codes before any implementation started. That made each prompt smaller and more precise, and it gave me a clear acceptance criterion to check whenever the AI proposed a change.

The coding agent was most useful when I gave it one issue at a time, along with the exact files and the failing test output. It generated the Prisma model, controllers, React components, and test cases quickly, but I still reviewed every diff against the specs and kept the edits inside the Lab 4 folders. Clear constraints mattered: the agent never had to guess which legacy file it was allowed to touch, so Labs 1 to 3 stayed intact.

Verification was part of the workflow rather than a final step. After each issue I ran type checking plus the Lab 4 API, UI, and Playwright suites, and the Resolution Gate tests caught regressions that would have been easy to miss in manual clicking. The biggest lesson is that Spec DD and TDD make AI assistance reliable: define the rule, write the test, let the agent implement, then prove the result with the real suite.
